# Ultra Moon scene and touch automation audit

Audit date: 2026-11-23, refreshed against root HEAD `da823ac6`. This is an evidence note only; no gameplay offsets or production behavior are changed here.

## Findings

- The generic 3DS policy currently treats every `Scene.FIELD` as touch-window-worthy, along with `MENU` and `SCREEN`. See [`DsStagePolicy.kt`](../app/src/main/kotlin/com/pokedaisy/app/DsStagePolicy.kt#L35).
- That is broader than the DS policy. The DS core supplies per-frame `FIELD_TOUCH` and, when enabled, `FIELD_TOUCH_BATTLE_MENU` flags; `EmulatorEngine.watchScreens()` derives `dsTouchWanted` from those bits and handles fade timing. It does not equate ordinary field play with a requested touch window. See [`EmulatorEngine.kt`](../app/src/main/kotlin/com/pokedaisy/app/EmulatorEngine.kt#L1524).
- **Correction against `da823ac6`: Ultra Moon's playable field is now mapped.** `Gen6Reader.configFor()` still has no USUM gameplay data config (`else -> null`), but its separate startup-module reader at `0x008B2000` returns `FIELD` when `FieldRo` is present, after checking the setup-screen modules (`LangSelect`, `HeroSelect`, `StrInput`). Other non-empty module sets remain `UNMAPPED`. The source comment records that an isolated Azahar run observed `FieldRo` together with `FieldMenu` and `FieldEffectCommon` while rendering the playable field; it also explicitly says this module signal does not enable gameplay memory data or Companion values. See [`Gen6Reader.kt`](../app/src/main/kotlin/com/pokedaisy/app/n3ds/Gen6Reader.kt#L395) and [`N3dsSession.kt`](../app/src/main/kotlin/com/pokedaisy/app/n3ds/N3dsSession.kt#L439).
- The null-config branch in `N3dsSession` still calls `startupSceneOf()` and `observeScene()`. A reported transition updates `scene`, then posts `onScene` to the UI thread. In `PokeDaisyActivity`, `onN3dsScene()` resets the auto-dismiss flag on scene changes and calls `syncGameScreen()`; the stage synchronizer computes `n3dsTouchAutoWanted` from `n3dsTouchWanted(scene, battleInput)`. Since `DsStagePolicy.n3dsTouchWanted()` returns true for every `FIELD`, entering a recognized Ultra Moon `FieldRo` scene makes the lower-screen presentation wanted even without a gameplay config. `syncN3dsStage()` then makes it visible. In ONE SCREEN / other floating layouts it is placed in a floating frame; SIDE BY SIDE keeps the chosen arrangement. Thus the existing policy **does apply** to ordinary Ultra Moon field play in this root revision. See [`N3dsSession.kt`](../app/src/main/kotlin/com/pokedaisy/app/n3ds/N3dsSession.kt#L500), [`PokeDaisyActivity.kt`](../app/src/main/kotlin/com/pokedaisy/app/PokeDaisyActivity.kt#L4505), and [`DsStagePolicy.kt`](../app/src/main/kotlin/com/pokedaisy/app/DsStagePolicy.kt#L35).
- The isolated captures available at `C:\Users\beben\Documents\Codex\pokedaisy\work\usum-scene-investigation\` include `ultra-moon-field-60.png`, `ultra-moon-field-a60.png`, `um-field-before-x.state`, and `um-field-x-menu.png` / `.state`. The two PNGs labeled as field and X-menu captures show the outdoor field on the top display and an all-black lower-display area. The X-menu-labeled capture therefore does not verify that the menu opened or that its touch page rendered. The adjacent `.state` files were not decoded or modified in this audit.
- The harness’s `shot` command writes the current top and bottom renderer buffers into a 400x480 image, placing the bottom at y=240; the lower black area is part of the captured renderer output, not unused PNG canvas. See [`n3ds_dump.cpp`](../native-capture/n3ds_dump/n3ds_dump.cpp#L108) and [`README.md`](../native-capture/n3ds_dump/README.md#L31). This establishes what those captures render, but does not explain why the bottom buffer is black.
- `rom-cro-symbol-inventory.txt` remains a static ROM inventory, not a runtime `modules` trace. The current `Gen6Reader.kt` source comment separately records the isolated Azahar runtime observation of `FieldRo`, `FieldMenu`, and `FieldEffectCommon` on the playable field. The supplied field PNGs still have no paired per-frame module/touch-state log, so they cannot independently establish scene timing or a game-requested lower-screen transition.

The captured lower renderer buffer is black even in the field and X-menu-labeled images. Because root HEAD now auto-presents that buffer on `FIELD`, the concrete risk is an automatically opened black/empty touch window during ordinary field play. The captures do not show whether the X menu was successfully opened, and therefore do not prove that the module-based `FIELD` classification matches the lower display's actual interactive state.

## PKMN-NTR reference

The public [PKMN-NTR 3.6-beta3 release](https://github.com/drgoku282/PKMN-NTR/releases/tag/3.6-beta3) describes USUM support for update 1.2. Its [LookupTable.cs](https://github.com/drgoku282/PKMN-NTR/blob/master/PKMN-NTR/Helpers/LookupTable.cs) lists US/UM candidates for trainer data (`0x33012818`, line 60), bag data (`0x33011934`, line 138), money (`0x33015210`, line 297), and party data (`0x33F7FA44`, with `0x330128E4` as an alternate, line 827). Those fields support data-reading research; they do not by themselves describe whether the bottom screen is visible or requests touch input.

The reference’s [Bot_SoftReset7.cs](https://github.com/drgoku282/PKMN-NTR/blob/master/PKMN-NTR/Bot/Bot_SoftReset7.cs) offers more relevant but still indirect probes:

- Its battle check reads `0x67107C` and expects the pointer value `0x304B742C` for US/UM (lines 136–170).
- Its menu routine explicitly presses X and then checks `0x6A60EA` for a value in `[0, 0x10000000)` (lines 204–221 and 1065–1081).
- After pressing A to open the bag, it checks `0x66EB54` for a value in `[0x01, 0x10001)` (lines 238–255 and 1097–1113).

These are candidate runtime predicates from an NTR bot flow, not verified PokeDaisy field/touch signals. The menu predicate is a range check, not a documented boolean flag. The headless field/X-menu captures listed above do not contain memory reads for those addresses, and this audit does not promote them into offsets or infer screen policy from them.

## Decision for follow-up

Unconditional `FIELD` is now active for Ultra Moon's recognized playable field, but it does not match the DS trigger contract: DS uses per-frame touch-request flags, while this USUM path uses a module name to classify field scene and then always requests the lower screen. That classification is enough to make automation active, but it is not evidence that the lower screen should be visible during all field play. Follow-up should correlate repeated module/scene reads and the candidate NTR menu/battle predicates with the captured lower buffer across field, X menu, and battle. Keep NTR offsets as investigation candidates only. No offsets were promoted, and this audit makes no production change.
