# Nintendo DS / 3DS integration parity

This comparison uses PokeDaisy's existing DS behavior (`docs/manual/devices.md`, `EmulatorEngine`, `DsStagePolicy`, and the shared Companion) and the user's Windows DS release as the interaction reference. It distinguishes the shipped Android behavior from the remaining Azahar work.

| Area | DS / Black 2 contract | Android 3DS implementation | Status |
| --- | --- | --- | --- |
| Session and Companion | DS runs through `EmulatorEngine` and its shared `SnapshotView` / Companion UI. | Azahar owns a separate `N3dsSession` thread and two Android surfaces. It reuses `GbaInput`, `SnapshotView`, the existing Companion UI, the shared screen stage, `GameActions`, and `StateSlots`; `load3ds()` no longer constructs an idle `EmulatorEngine`. | Controlled refactor: share PokeDaisy's core-neutral actions and state-slot UI while keeping Azahar's run loop and surfaces under `N3dsSession`. The DS `EmulatorEngine` remains the DS core adapter. |
| Scene source | The melonDS integration exposes game scene/touch flags to `EmulatorEngine.watchScreens()` every frame. Black/White/Black 2/White 2 menus and battles select a paired or floating touch presentation by game state. | `N3dsSession` reads Azahar CRO modules and title-specific `Gen6Reader.Config` data every 100 ms, then applies shared stage policy. | Partial: state input exists for configured X/Y, ORAS and Sun/Moon. Ultra Moon has no gameplay map. |
| ONE SCREEN | The main game fills the display; the touch screen floats in for the game's mapped interaction pages. DS menus may temporarily pair both screens; manual TOUCH SCREEN remains available. | 3DS keeps the player's selected DS layout. Mapped field, menu, both-screen setup pages, and battle bag/party request the shared floating touch-screen window in ONE SCREEN; explicit layouts stay explicit. | Partial: Ultra Moon recognizes its observed language, hero-selection and name-entry setup pages; field, menu and battle remain `UNMAPPED`. |
| Transitions | DS reads core fade/dark-screen flags each frame and holds the previous composition until the next page is ready, with a 600-frame watchdog. | 3DS samples and caches a paired top/touch image during stable scenes, then layers the last cached pair above both live surfaces when a scene candidate appears. | Partial: 100 ms scene polling does not observe per-frame brightness fades or transitions within one scene. If scene evidence stays missing or unstable, a 100-read watchdog releases the held pair after 10 seconds without guessing a new scene. |
| Touch input | The game gets touch coordinates in its native touch-screen space; the active layout and floating window do not change their meaning. | `N3dsNative.touch` sends coordinates through Azahar's active window/layout mapping. | Implemented in the bridge; physical S25 touch interaction remains unverified because the phone was locked during the latest update. |
| Companion | Shared Companion UI consumes the DS core's game-specific RAM reader; Windows DS refreshes visible telemetry every 12 frames. Black 2's party/battle state is available through its Gen 5 reader. | Shared snapshot/UI consumes `Gen6Reader.Config`; mapped 3DS snapshots now refresh every 200 ms. | Partial: the reader currently maps X/Y, ORAS and Sun/Moon. Ultra Sun/Moon have no verified config, so Companion data correctly reports unavailable. |
| Field HUD / zoom | The shared DS HUD follows verified field state and yields during menus/battles. | 3DS has a separate Gen 6 HUD/camera adapter for configured titles. Azahar camera zoom is not the same mechanism as DS EXPAND. | Partial and title-dependent; Ultra Moon live fields are unavailable until its config is verified. |

The scene-thread observation batches the directly mapped X/ORAS field-hold word with its CRO and battle-controller read at the same Azahar frame boundary. Sun/Moon's pointer-chained hold word still requires guarded follow-up reads. A paired Vulkan readback is cached every ten stable scene observations (about one second); a scene candidate reuses that cached pair so its overlay starts from an image sampled before the change. If the newer combined-observation JNI entry point is unavailable, the scene thread logs the mismatch once and falls back to the older separate reads. This still does not detect per-frame brightness fades or transitions whose mapped scene does not change.

## Architecture decision record (2026-11-23)

**Decision: controlled refactor (Option A).** The original PokeDaisy architecture remains the authority for player-facing actions, telemetry, screen staging, and Companion UI. Azahar owns its required native frame loop, Vulkan surfaces, and memory-read boundary; forcing these through `EmulatorEngine` would create a second, fake DS-style loop around the core rather than a useful shared interface.

| Classification | Components and decision |
| --- | --- |
| KEEP | `N3dsSession` as Azahar lifecycle/input adapter; `N3dsNative` and `pk_n3ds_jni.cpp` as the JNI boundary; verified title-specific `Gen6Reader` configs; `N3dsSaves`; `N3dsSnapshotGate` / `N3dsSnapshotHealth`; shared `SnapshotView`, telemetry, Companion screens, `GbaInput`, and DS stage/layout policy. |
| REFACTOR | `PokeDaisyActivity` wires 3DS to the same `GameActions` and `StateSlots` contracts as DS. Its 3DS slot index and Azahar savestate calls live in the host adapter, not an unrelated idle engine. Scene polling, native observation batching, and paired transition captures remain behind the 3DS adapter and its testable `N3dsSceneTransition`. |
| REMOVE | The no-op `EmulatorEngine` construction from `load3ds()`. It existed only to satisfy code paths that could instead depend on `GameActions` / `StateSlots`; those core-neutral bridges now serve 3DS directly. |
| REPLACE | No Azahar loop or verified memory reader is replaced. A shared emulator-session interface is deferred until at least two cores can use the same lifecycle contract without hiding material differences. |

This keeps the native boundary small and the user-facing path shared. It also limits the rewrite risk and retains the existing title research. The remaining architectural differences are Azahar's asynchronous `N3dsSession`, its 100 ms scene reads instead of DS per-frame observation, and Android surface composition for its two outputs. These differences follow Azahar's threading/rendering model; current work reduces duplicate app behavior without claiming identical timing or complete parity. Ultra Moon still has no verified gameplay memory configuration, so neither its gameplay scenes nor Companion data are inferred from Sun/Moon.

The shared 3DS host now also uses `GbaInput.frameMask()` for the same two-frame turbo cadence, converts analog L2/R2 through PokeDaisy hotkeys without requiring an `EmulatorEngine`, restores the shared fast-forward toggle when a session starts, and releases controller-owned holds on pause. The 3DS state screen disables UNDO actions because the Azahar adapter does not yet use `StateSlotController`'s undo transaction; the keys are no longer consumed as successful no-ops.

The optional `n3ds` build now adds Azahar and the verified static-link dependency license texts to Settings > LICENSES without requiring the submodule for regular builds or CI. Redistribution is still blocked on a compatibility review: the pinned Azahar tree contains both GPLv2 and GPLv3-or-later notices, FAAD2 states a GPL-only restriction, and its generated GLAD loader has no license file in the pinned tree. See `NOTICE` and `app/build.gradle.kts`; no license-compliance claim is made yet.
| 3DS core choice | DS exposes the app's available DS cores and their real capabilities. | Settings resolve `AUTO` / `AZAHAR` to the one bundled native Azahar backend. | Honest single-backend wiring; the Windows release contains no 3DS core or second Azahar backend. |
